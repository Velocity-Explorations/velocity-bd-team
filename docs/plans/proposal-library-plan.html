Proposal Library Plan

Six phases that turn a curated Drive folder of past submissions, plus a hand-built register of outcomes and strength ratings, into retrieval the reviewer and the drafter can use. The result: when the scanner judges a new call, it sees what Velocity submitted to similar calls before, how strong the team thought each was, and whether it won.

Your setup, step by step

This plan has more human work than the scanner playbook, and all of it is front-loaded. Steps 1 to 2 happen before Phase A; step 3 is the hand-curation that happens after the bot pre-fills the Register.

1. Build the Drive folder (before Phase A)

  1. In Google Drive (Velocity account), create a folder named BD Proposal Library. Don't put it inside another shared folder; a top-level My Drive or Shared Drive folder is easiest to find.
  2. Inside it create two folders: 01 Company Reference and Submissions. Leave the README and Register for the bot to create in Phase A.
  3. Into 01 Company Reference, upload the reusable material: capabilities statement, boilerplate, past-performance write-ups, personnel bios, win themes. Use current, curated versions of these; nothing from the old Yukon project goes on the work Drive. (The repo keeps its own copy of the old knowledge-base files under reference/yukon/knowledge-base/ purely as the Writer's fallback until this folder is populated.)
  4. For each past submission, inside Submissions create one folder named YYYY-MM-DD_portal_short-title using the date you submitted and a slug from the list above (e.g. 2026-05-13_vulcan-sof_jatf-26-collective-autonomy). Lowercase, hyphens, no spaces.
  5. Inside each, create 00_solicitation, 01_submitted, 02_working, 03_outcome. Empty subfolders are fine.
  6. Put the as-submitted files in 01_submitted, renamed to describe the volume (technical-volume.pdf, cost-volume.xlsx, quad-chart.pptx, white-paper.pdf). For Vulcan, export or screenshot the on-portal submission to PDF and include it; the narrative text otherwise never reaches the Proposal Library.
  7. Put the call/RFI/BAA text and attachments in 00_solicitation, anything the government sent back in 03_outcome, drafts in 02_working if you want to keep them.
  8. Do the Vulcan submissions first (JATF-26 Collective Autonomy, Tactical Edge PNT, Vigilant Eagle 27 are the known ones), then anything that won, then the rest as time allows. The bot handles folders being added later.

2. Folder ID and access (before Phase A)

  1. Open BD Proposal Library in the browser. The URL ends with /folders/<long id>; copy that id.
  2. Add to the repo's .env: LIBRARY_DRIVE_FOLDER_ID=<that id>.
  3. Confirm gog can see it from a terminal: gog drive ls <that id> --account david@velocityexplorations.com (or the equivalent list command). If the folder is in a Shared Drive and it isn't listed, share the folder with the account gog is authenticated as.

3. Fill the Register (after Phase A pre-fills it)

The bot creates the sheet with one row per folder and the dates and portal already filled. You add the judgment. Work one row at a time, Vulcan rows first.

  • outcome: pick one. pending if you're waiting; no_award if the government never awarded anyone; lost if someone else won; shortlisted if you made a down-select but hadn't heard further; withdrawn if you pulled it. Never leave it blank.
  • strength_rating (1 to 5): how strong you thought the submission was when you sent it, not in hindsight. 5 = we were the obvious fit and the writing was tight; 3 = credible but a stretch somewhere; 1 = we knew it was a long shot.
  • strength_reason: one or two sentences on why. "Direct Echo C2 fit, had the right past performance" or "Needed a hardware partner we didn't have."
  • why_won_or_lost: the debrief in your own words if you got one; what you believe if you didn't; no debrief if you have nothing. Don't skip it on losses; losses teach the bot more than wins.
  • use_as_exemplar: yes only for submissions you'd be happy to have the bot write like. Usually that's wins plus one or two strong losses. Aim for 3 to 8 exemplars total, not everything.
  • themes: a few comma-separated keywords (C2, autonomy, NLP, modernization, edge AI, PNT). These boost retrieval, so use the words you'd search for.
  • type, agency, solicitation_id, role, requested_value: fill what you know; blanks are fine.

When you've done a batch, tell the agent to run --sync-register; it reports any row it couldn't accept and why.

## Context

The one-database rule: embeddings live in the same PostgreSQL as everything else, using the pgvector extension (enable it on the hosted instance; Neon and Supabase both support it). For local SQLite development, store vectors as JSON text and do brute-force cosine in Python; the query interface must be identical.

Embedding model: use whatever embedding endpoint this environment has, behind `library/embed.py: embed(texts: list[str]) -> list[list[float]]`, with the model name and dimension recorded in config so a model change triggers a full re-embed. The reference implementation used Ollama `nomic-embed-text` (768 dims) locally; that is an acceptable fallback.

Chunking: ~2000 characters per chunk, split on paragraph boundaries where possible, 200-character overlap. Keep chunks from `01_submitted/` and `03_outcome/` always; chunk `00_solicitation/` too (it teaches "what was asked"); chunk `02_working/` only if the file is under 50 pages. Reference documents (`_reference/`) are chunked with submission_id NULL.

## Tasks

1. `library/extract.py`: text extraction for .docx (python-docx, include table cell text), .pdf (pypdf or pdfplumber; fall back to OCR only if a page yields no text and an OCR tool is available), .pptx (slide text + notes), .xlsx (sheet name + cell text, row by row). Return plain text. Save it next to the file as `.txt` so re-chunking doesn't re-extract.
2. Migration: `proposal_chunks(id PK, document_id FK, submission_id, subfolder, chunk_index, text, embedding vector(DIM) | TEXT, portal, outcome, strength_rating, use_as_exemplar, type, themes, submitted_date)`: the register columns are denormalized onto every chunk so filtering is one query. Index: ivfflat or hnsw on embedding (Postgres only). Update `docs/LEDGER_SCHEMA.md`.
3. `library/ingest.py`: for every document with extracted_at NULL: extract, chunk, embed in batches of 32, insert chunks, set extracted_at and chunk_count. Re-ingest deletes the document's old chunks first. Log per document: filename, chunks, seconds.
4. Briefs: for every proposal with brief NULL (or `--rebrief`), build a prompt from up to the first 6000 characters of 01_submitted/ text plus the register row, and ask the LLM for one paragraph: what was proposed, to whom, the core technical approach, the claimed differentiators, and (if outcome is known) the outcome in one clause. Store in `proposals.brief`. Keep under 120 words.
5. `library/search.py`: `search(query, k=8, portal=None, outcome=None, exemplar_only=False, subfolders=None) -> list[chunk + score]` using cosine similarity, with the same signature on Postgres and SQLite.
6. Add `--ingest` and `--rebrief` to the library CLI; the daily job runs `--ingest` after the drive sync.

## Context

When the scanner evaluates a new call, the reviewer should see: the most similar past submissions, each with its outcome and the team's strength rating, and a one-line history of how Velocity has done on this portal. Won and strongly-rated submissions are positive evidence of fit; lost or weak ones are still evidence the team considered the area relevant, just weaker. Absence of any similar submission is not negative evidence.

The block must stay short: the review prompt already carries the company profile and recent human decisions, and the model has a 35-second budget.
