PHASE W0

Port the pipeline

A mechanical port: every phase becomes a pure function (text in, text out) calling one shared LLM client, with the old prompts copied verbatim. No ledger, no corpus, no Drive yet; the pipeline runs from a JSON file to a local folder so it can be tested without touching anything live.

Depends on: the repo (Playbook Phase 0) and reference/yukon/. Produces: drafting/pipeline.py, drafting/llm.py, drafting/templates/, a file-in/folder-out CLI.
Prompt · Phase W0
You are working in the `velocity-bd-team` repository as the Writer agent. You own `drafting/`. This is Writer Phase W0 of 4: port the proven RFP response pipeline from `reference/yukon/rfp_response_agent.py` into `drafting/` with the same phases and the same prompts, but with clean plumbing. Read AGENTS.md first; work on a branch `writer/w0-port` and open a PR.

## Context

The reference script generates a complete proposal response in phases: 1 scrape the listing page, 2 download attachments (SAM.gov only), 3 retrieve similar past submissions, 4 extract requirements (including a "SOLICITATION TERMINOLOGY & KEYWORDS — SOURCE OF TRUTH" section), 4.5 alignment assessment, 5 outline with page budget, 6 draft with evidence-first rules, 6.5 four sequential review passes (government evaluator, second evaluator, company leadership, capability verification), 6.75 mechanical compliance check (outputs a report and a corrected draft split on `---CORRECTED DRAFT---`), 7 submission checklist, 7.5 format polish, 8 deliver. Templates per opportunity type live in `reference/yukon/templates/` and are chosen by `TEMPLATE_MAP`.

The phase prompts are trusted; copy them verbatim. The plumbing is not: it shells out to `claude -p` with a Popen keepalive loop, takes the opportunity as a JSON argument, queries ChromaDB directly, and reports progress to a web API that no longer exists. Replace all of that. The pipeline has never been run end-to-end live, so expect to find bugs in phase hand-offs; fix plumbing bugs, do not rewrite prompts.

## Tasks

1. `drafting/llm.py` — `generate(prompt, system="", model=None, max_tokens=8000, timeout=600, phase_label="") -> str` using the Anthropic API (ANTHROPIC_API_KEY) with streaming so long phases don't idle a connection; model default claude-sonnet-5-5, overridable per call; retries once on transient errors; logs prompt length, output length, and seconds per call; raises a `PhaseError` with the phase label on failure. Never log prompt contents above DEBUG.
2. `drafting/templates/` — copy every `.md` from `reference/yukon/templates/` and port `TEMPLATE_MAP` into `drafting/templates/__init__.py` as `select_template(opp_type) -> (name, text, is_fallback)`.
3. `drafting/prompts.py` — every phase prompt from the reference, verbatim, as functions that take their inputs and return the prompt string. Keep the phase numbers in the function names (`p4_requirements`, `p45_alignment`, `p5_outline`, `p6_draft`, `p65_review_pass(n)`, `p675_compliance`, `p7_checklist`, `p75_polish`).
4. `drafting/pipeline.py` — `run_pipeline(inputs: DraftInputs, out_dir: Path, hooks: Hooks) -> DraftOutputs` where DraftInputs holds: title, portal, opp_type, agency, due_date, url, description, listing_text, attachments (list of {name, text}), past_experience (str), company_context (str), template (name, text). Each phase is a function `phase_xx(inputs, state, out_dir, hooks) -> state`; the pipeline runs them in order, writes each phase's output to `out_dir` with the same filenames as the reference (`requirements.md`, `alignment.md`, `outline.md`, `draft.md`, `draft_review_pass{1-4}.md`, `draft_v2.md`, `compliance_report.md`, `draft_v3.md`, `checklist.md`, `draft_final.md`), and calls `hooks.progress(phase, status, message)` before and after each. A phase failure logs, records it, and continues with the previous best draft (the reference's fallback chain `draft_final → draft_v3 → draft_v2 → draft`). Support `--from-phase` to resume from saved files.
5. `drafting/cli.py` — `python -m drafting.cli --inputs inputs.json --out data/drafting/<slug>/ [--from-phase 5] [--model ...]`. Hooks print to stdout. No ledger, corpus, Drive, or Slack in this phase.
6. Tests: one unit test per phase using a fake `generate` that returns canned text, asserting the right files are written and the fallback chain works when a phase raises; one test that `select_template` maps every TEMPLATE_MAP key and falls back to `full_proposal`.

- Tests pass. The PR touches only `drafting/` and `tests/`.

Depends on: W0, Playbook Phase 8 (calls with human_status = 'pursue'), Corpus Phase E. Produces: drafting/inputs.py, --call-id.
Prompt · Phase W1
You are working in the `velocity-bd-team` repository as the Writer agent. ## Context

The ledger's `calls` table holds every scraped opportunity (id like `vulcan-<uuid>`, portal, title, type, department, due_date, url, description, extra JSON, human_status, human_notes). A call is ready to draft when `human_status = 'pursue'`. The Librarian's `corpus/exemplars.py` provides `drafting_context(query, portal=None, budget_chars=12000) -> str` (exemplar passages, the solicitations they answered, evaluator feedback, company reference material). The corpus's `_reference/` text (capabilities, boilerplate, bios, win themes) replaces the old knowledge-base injection.

Listing text: for Vulcan SOF, the call page requires login; reuse `portals/vulcan_sof/auth.login` and the same page-text extraction the scraper uses, via a function the portal agent exposes as `PORTAL["fetch_full_text"](page, url) -> {"text": str, "attachments": [{"name", "url"}]}`. If a portal doesn't expose it, fall back to `description`. For SAM.gov, port the attachment download from the reference (`phase_download_attachments`) behind the same interface, to be wired when that portal agent exists.

## Tasks

1. `drafting/inputs.py` — `build_inputs(call_id) -> DraftInputs`: load the call; refuse with a clear message if human_status isn't 'pursue' (override with `--force`); map `calls.type` to `opp_type` using the reference's `_resolve_opp_type` logic; fetch full listing text and attachment text through the portal's `fetch_full_text` with a 120s cap, caching under `data/drafting/<call_id>/source/`; build `past_experience` from `drafting_context(title + description, portal=slug)`; build `company_context` from the corpus reference material (fall back to `reference/yukon/knowledge-base/*.md` if the corpus isn't ingested yet); select the template.
2. Ask the portal agents, via a GitHub issue per portal, to expose `fetch_full_text` in their `PORTAL` dict; implement the Vulcan one yourself in this PR only if the Vulcan agent agrees in the issue, otherwise fall back to description and note it.
3. CLI: `python -m drafting.cli --call-id vulcan-… --out data/drafting/<call_id>/`. Keep `--inputs` for fixtures. Write the resolved `DraftInputs` to `source/inputs.json` so a run is reproducible.
4. Record `human_notes` from the call in the inputs and pass it into the alignment prompt as "Team notes on this pursuit:", because the person who marked it pursue usually said why.

Prompt · Phase W2
You are working in the `velocity-bd-team` repository as the Writer agent. Phases W0–W1 produced a pipeline that drafts from a `--call-id` into a local folder. This is Writer Phase W2: deliver outputs to the right places, report progress, and let the team trigger a draft. Branch `writer/w2-deliver`.

## Context

Corpus conventions: each submission has a Drive folder `Submissions/<submission_id>/{00_solicitation,01_submitted,02_working,03_outcome}/` where `submission_id = YYYY-MM-DD_portal_short-title`, and a row in the Register sheet and the ledger's `proposals` table. The Writer's drafts are working documents, so they go in `02_working/`. The Librarian's `corpus/register.py` can create a Register row (`create_register_row(fields)`) and `ledger.queries.upsert_proposal` writes the table. Slack delivery (`slack/sink.py`) posts one card per call and stores `calls.slack_channel` / `slack_ts`; the Writer reports into that card's thread. Phases can run 5–20 minutes each, so the old pipeline posted a keepalive ("⏳ Still drafting… (3m elapsed)") every 60 seconds; keep that.

## Tasks

1. `drafting/progress.py` — a `Hooks` implementation that: creates a `runs` row with component 'writer' and the call id in stage_counts at start and finishes it at the end; posts one thread reply per phase start/finish under the call's Slack card; while any single LLM call runs longer than 60s, posts "⏳ Still <phase>… (Nm elapsed)" every 60s on a background timer; posts a final summary with links.
2. `drafting/deliver.py` — at the end of a run: compute `submission_id` (today's date, portal slug, slugified title ≤40 chars; reuse an existing `proposals.source_call_id` match if one exists so re-drafts don't create duplicates); create the Drive folder tree if absent; upload to `02_working/` the six documents the reference delivered (Requirements Analysis, Alignment Assessment, Proposal Outline, Draft Response, Compliance Report, Submission Checklist) as Google Docs converted from markdown, plus the source listing text to `00_solicitation/` if that folder is empty; create the Register row and `upsert_proposal` with outcome 'pending', type from opp_type, source_call_id = call id; store the folder link in `calls.extra["draft_folder"]`.
3. Trigger: a Slack reaction ✍️ (`:writing_hand:`) on a call card, or the dashboard's "Draft" button, sets `calls.extra["draft_requested_at"]`; a `python -m drafting.cli --pending` run picks up every call with that flag and no completed writer run, drafts it, and clears the flag. Add `--pending` to the daily schedule after the scanner. Never draft a call that isn't human_status 'pursue', even if flagged.
4. Idempotence: re-running for the same call reuses the submission folder and overwrites the working docs; it never creates a second Register row.

## Done when

- A real run from `--call-id` ends with: a Drive folder in the corpus with six docs in `02_working/`, a Register row and `proposals` row with outcome pending and source_call_id set, a `runs` row with component 'writer' and status completed, and a Slack thread under the call's card showing phase messages, at least one keepalive, and a final summary with the folder link.
- Running it again for the same call updates the docs in place and creates no new rows (show counts before and after).
- React ✍️ on a card whose call is 'pursue', run `--pending`: it drafts. React ✍️ on one that is not 'pursue': it is skipped with a thread reply explaining why.

PHASE W4

Exemplar-driven drafting

The first genuinely new capability, and the reason the corpus exists: the draft phase writes in the voice of your strongest winning submissions, the alignment phase cites real past performance with outcomes, and the review passes check the draft against evaluator feedback you actually received. Only worth doing once W3's fix list is closed and the Register has a few rated, outcome-known rows.

Depends on: W3, Corpus Phases C–E with exemplars flagged. Produces: exemplar injection in phases 4.5, 6 and 6.5; a before/after comparison.
Prompt · Phase W4
You are working in the `velocity-bd-team` repository as the Writer agent. Phases W0–W3 produced a pipeline that runs end-to-end on live calls, with a findings document and approved prompt changes. This is Writer Phase W4: make the corpus shape the writing. Branch `writer/w4-exemplars`.

## Context

The Librarian's `corpus/exemplars.py` provides `find_exemplars(query, portal, k, require_exemplar=True, prefer_won=True)` (passages from submissions the team flagged as exemplars, each paired with the solicitation excerpt it answered), `find_feedback(query, portal, k)` (evaluator feedback and debriefs from `03_outcome/`, wins and losses), and `find_reference(query, k)` (company material). The Register carries outcome and strength_rating per submission. Until now the Writer used only the combined `drafting_context()` block in the retrieval phase. This phase threads targeted retrieval into the phases where it changes the writing.

## Tasks

1. Phase 4.5 alignment: replace the generic past-experience block with `find_exemplars` results filtered to won/shortlisted plus `find_reference` past-performance write-ups, and instruct the prompt to cite them by submission title with outcome ("as demonstrated in <title> (won, 2026)"). Never cite a lost submission as past performance; losses may inform gaps only.
2. Phase 6 draft: for each major outline section, retrieve up to two exemplar passages on that section's topic and pass them under "WRITE IN THIS VOICE — passages from our strongest submissions (do not copy; match tone, structure, and specificity)". Keep the total exemplar text under 8K chars per section call; if the draft is generated in one call, cap at 12K total and prefer section-level generation when the outline has more than six sections.
3. Phase 6.5 review pass 1 (government evaluator): add `find_feedback` results under "EVALUATOR FEEDBACK WE HAVE RECEIVED BEFORE — check the draft against each point", so the review catches the mistakes that cost points last time.
4. Record in `runs.stage_counts` which submission_ids were used in each phase, and write them to the Alignment Assessment document's footer so a human can see the lineage.
5. Comparison: re-run the W3 call with `--no-exemplars` and with exemplars, from phase 4.5. Produce `docs/WRITER_EXEMPLAR_COMPARISON.md` with side-by-side excerpts of the alignment and two draft sections, and the metrics for both runs.
