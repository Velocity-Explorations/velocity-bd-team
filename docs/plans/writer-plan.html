When someone asks for a draft

There are three ways to ask, one queue, and one worker. Every request becomes a row in the ledger's drafts table. A worker on the PC picks it up within about 20 seconds and runs the pipeline in its own process. Slack and the dashboard both show progress from that row, and the dashboard is where people act on it. Run the Draft-Ready Upgrade U1 first; it adds the queue this relies on.

  1. Ask. Click Draft response on the dashboard, ask the assistant in Slack, which records a draft request that someone approves on the dashboard's Requests page, or run drafting.cli request. For a solicitation no scanner found, such as an emailed RFP, use request --manual with the files.
  2. Checks. The request is refused, with the reason shown where it was made, if the call is marked not relevant, dismissed or submitted, or if a draft for it is already queued or running. Otherwise the call is marked "pursue" and a queued draft is created.
  3. Start. The worker runs one draft at a time, estimates its cost first, and holds it for an approver if the estimate is over the cap.
  4. Progress. One status message in the card's thread updates in place, for example "phase 7 of 12, 14m elapsed". The dashboard shows the same.
  5. Control. Cancel on the dashboard stops a draft within about two minutes. Retry resumes a failed or cancelled draft from the phase where it stopped. An approver clicks Approve to release a draft that's over budget.
  6. Delivery. Six Google Docs land in the submission's 02_working/ folder on Drive, with one Register row (outcome pending). A reply in the thread, also shown in the channel, gives the link, word count, page estimate, open compliance items, time and cost.

Decisions are made on the dashboard, and Slack informs. The status message and the completion reply appear in the card's thread, but nothing in Slack starts, stops or approves a draft. In the retired Yukon system a 👍 on a card started a draft on its own. Here marking a call Pursue never costs a draft, because drafting is always a separate, deliberate request.

## Context

The reference script generates a complete proposal response in phases: 1 scrape the listing page, 2 download attachments (SAM.gov only), 3 retrieve similar past submissions, 4 extract requirements (including a "SOLICITATION TERMINOLOGY & KEYWORDS: SOURCE OF TRUTH" section), 4.5 alignment assessment, 5 outline with page budget, 6 draft with evidence-first rules, 6.5 four sequential review passes (government evaluator, second evaluator, company leadership, capability verification), 6.75 mechanical compliance check (outputs a report and a corrected draft split on `---CORRECTED DRAFT---`), 7 submission checklist, 7.5 format polish, 8 deliver. Templates per opportunity type live in `reference/yukon/templates/` and are chosen by `TEMPLATE_MAP`.

The phase prompts are trusted; copy them verbatim. The plumbing is not: it shells out to `claude -p` with a Popen keepalive loop, takes the opportunity as a JSON argument, queries ChromaDB directly, and reports progress to a web API that no longer exists. Replace all of that. The pipeline has never been run end-to-end live, so expect to find bugs in phase hand-offs; fix plumbing bugs, do not rewrite prompts.

## Tasks

1. `drafting/llm.py`: `generate(prompt, system="", model=None, max_tokens=8000, timeout=600, phase_label="") -> str` using the Anthropic API (ANTHROPIC_API_KEY) with streaming so long phases don't idle a connection; model default claude-sonnet-5-5, overridable per call; retries once on transient errors; logs prompt length, output length, token usage and seconds per call; raises a `PhaseError` with the phase label on failure. Never log prompt contents above DEBUG. Make an in-flight stream abortable from another thread, because later phases cancel drafts mid-call.
2. `drafting/phases.py`: the ordered phase list with ids and display names: 1 Listing, 2 Attachments, 3 Past experience, 4 Requirements, 4.5 Alignment, 5 Outline, 6 Draft, 6.5 Review ×4, 6.75 Compliance, 7 Checklist, 7.5 Polish, 8 Deliver. Everything that reports progress uses these names.
3. `drafting/templates/`: copy every `.md` from `reference/yukon/templates/` and port `TEMPLATE_MAP` into `drafting/templates/__init__.py` as `select_template(opp_type) -> (name, text, is_fallback)`.
4. `drafting/prompts.py`: every phase prompt from the reference, verbatim, as functions that take their inputs and return the prompt string. Keep the phase numbers in the function names (`p4_requirements`, `p45_alignment`, `p5_outline`, `p6_draft`, `p65_review_pass(n)`, `p675_compliance`, `p7_checklist`, `p75_polish`).
5. `drafting/pipeline.py`: `run_pipeline(inputs: DraftInputs, out_dir: Path, hooks: Hooks, from_phase=None) -> DraftOutputs` where DraftInputs holds: title, portal, opp_type, agency, due_date, url, description, listing_text, attachments (list of {name, text}), past_experience, company_context, team_notes, template (name, text). Each phase is a function `phase_xx(inputs, state, out_dir, hooks) -> state`; the pipeline runs them in order, writes each phase's output to `out_dir` with the reference's filenames (`requirements.md`, `alignment.md`, `outline.md`, `draft.md`, `draft_review_pass{1-4}.md`, `draft_v2.md`, `compliance_report.md`, `draft_v3.md`, `checklist.md`, `draft_final.md`), and calls `hooks.phase_started(phase)` and `hooks.phase_finished(phase, status, stats)` around each. A phase failure is recorded and the pipeline continues with the previous best draft (the reference's fallback chain `draft_final → draft_v3 → draft_v2 → draft`). With from_phase set, earlier phases load their saved files instead of running.
6. `drafting/cli.py`: a subcommand CLI. This phase adds `dev`: `python -m drafting.cli dev --inputs inputs.json --out data/drafting/<slug>/ [--from-phase 5] [--model ...]`. Hooks print to stdout. No ledger, Proposal Library, Drive or Slack in this phase.
7. Tests: one unit test per phase using a fake `generate` that returns canned text, asserting the right files are written and the fallback chain works when a phase raises; one test that `select_template` maps every TEMPLATE_MAP key and falls back to `full_proposal`.

PHASE W2a

Draft queue and worker

Writer

Turns a request into a job. An always-on worker claims queued drafts from the ledger and runs each one as a separate process, so a crash in one draft can't take down the worker. The worker checks cost before spending, writes progress into the draft's row, stops within about two minutes when cancelled, and keeps everything on disk so a retry resumes where it stopped.

The worker never calls Slack. It only writes the ledger; W2b renders that row in Slack and on the dashboard. Everything here can be tested from the command line before any button exists.

Depends on: W1, the drafts table with its helpers from the Draft-Ready Upgrade (U1), and the change_requests table that holds approved draft requests. Produces: drafting/worker.py, drafting.cli run/request/cancel/retry/approve/status, manual requests, a scheduling PR.
Prompt · Phase W2a
You are working in the `velocity-bd-team` repository as the Writer agent. You own `drafting/`. Phases W0 to W1 produced `drafting/pipeline.py` (`run_pipeline(inputs, out_dir, hooks, from_phase)`), `drafting/phases.py` (the ordered phase list), `drafting/inputs.py` (`build_inputs(call_id)`) and `drafting.cli dev`. This is Writer Phase W2a: turn a draft request into a queued, visible, cancellable job. Branch `writer/w2a-queue`. The dashboard buttons that create requests come in W2b, built by the Dashboard agent; everything here is driven from the CLI and the ledger.

## Context

The request contract lives in the ledger (see docs/LEDGER_SCHEMA.md):
- A request is a `drafts` row with status 'queued', created by `ledger.queries.request_draft(call_id, by, via)` or the equivalent SQL from the dashboard. Only one queued, needs_approval or running draft may exist per call; a partial unique index enforces it. A request sets the call's human_status to 'pursue' if it was empty and is refused for calls marked not_relevant, dismissed or submitted.
- `request_cancel` cancels a queued or needs_approval draft at once and sets cancel_requested_at on a running one. `request_retry` creates a new queued draft whose resume_of points at the failed or cancelled one. `approve_draft` moves a needs_approval draft back to queued.
- Draft requests from the assistant: the portal assistant's `propose_draft` records a `change_requests` row of kind 'draft'. A person approves it on the dashboard's Requests page, and it then waits with status 'approved' for you; `run.py --apply-requests` leaves drafts alone. Turning those into queued drafts is your job (task 1e).
- You, the worker, are the only thing that moves a draft from queued to running, completed or failed, or a running draft to cancelled. Progress goes into the row: current_phase, phase_log, heartbeat_at, estimate_usd, cost_usd, result, error. Slack and the dashboard render that row; you never call Slack.

A draft runs 20 to 60 minutes and makes many long model calls. So: one at a time by default, cost checked before starting, a cancel must stop spending within about a minute, and a crash must leave enough on disk to resume.

## Tasks

1. `drafting/worker.py`: `python -m drafting.worker`, a long-running loop with a 20-second tick:
   a. Reap: a running draft whose heartbeat_at (or started_at, if it has no heartbeat yet) is more than 10 minutes old, or whose worker_pid is no longer alive, becomes 'failed' with error "draft process stopped unexpectedly".
   b. Enforce cancels: a running draft with cancel_requested_at set should exit by itself within 60 seconds (task 2d). If its process is still alive 2 minutes after the request, kill the whole process tree (on Windows `taskkill /PID <pid> /T /F`, which also ends Playwright's Chromium) and mark it 'cancelled'.
   c. Claim: while fewer than DRAFT_MAX_CONCURRENT (default 1) drafts are running, claim the oldest queued draft atomically (`UPDATE drafts SET status='running', started_at=… WHERE id=? AND status='queued'`, then check the row count) and start `python -m drafting.cli run --draft-id N` as a child process logging to `data/drafting/<call_id>/draft_<N>.log`. Store its pid.
   d. Drafts never run inside the worker process. Log one line per state change to `data/drafting/worker.log`.
   e. Approved draft requests: for each `change_requests` row with kind 'draft' and status 'approved', claim it with `ledger.queries.claim_request(id)`, call `request_draft(call_id, by=<its requested_by>, via='assistant')`, and finish it with `finish_request(id, 'applied', 'Queued as draft N')`, or `finish_request(id, 'failed', <the refusal reason>)` when request_draft refuses.
2. `python -m drafting.cli run --draft-id N`: the child process:
   a. Load the draft and its call. work_dir = `data/drafting/<call_id>/`, shared by retries of the same call. Call `build_inputs(call_id)`.
   b. Initialize phase_log with every phase from drafting/phases.py in order (id, name, status 'pending'). For a retry (resume_of set), mark the phases that completed in that earlier draft as 'resumed' and start at the first one that didn't.
   c. Cost gate: before the first model call, estimate the run's cost from the source text sizes and the phase structure, using per-model prices kept in `drafting/config.py` (look them up and record where and when). If the estimate exceeds DRAFT_BUDGET_USD (default 10; revisit after W4's measured run) and approved_by is empty, store estimate_usd, set status 'needs_approval', and exit cleanly. After `approve_draft`, the worker claims it again and the gate passes.
   d. Run the pipeline with hooks that set current_phase and update that phase's phase_log entry (status running, completed or failed; start and finish times; seconds; characters in and out) on every start and finish; refresh heartbeat_at at least every 60 seconds from a background timer; and check cancel_requested_at at every phase boundary and every heartbeat. On cancel: abort the in-flight model stream, mark the phase 'cancelled', set the draft 'cancelled', and exit without delivering.
   e. Success: status 'completed', finished_at, cost_usd from actual token usage, and result JSON: word_count of the final draft, page_estimate at 450 words per page, page_limit if the requirements found one, compliance_open_items counted from compliance_report.md, alignment_fit from alignment.md. Failure: status 'failed' with the phase and the first 300 characters of the error. Phase files stay in work_dir either way.
3. CLI for people and tests: `request --call-id X [--by NAME] [--force]` (calls request_draft with via 'cli' and prints the draft id or the refusal reason; --force skips the status check), `cancel --call-id X`, `retry --call-id X`, `approve --draft-id N --by NAME`, `status [--call-id X]` (recent drafts with status, phase, elapsed and cost).
4. Manual requests: `request --manual --title "…" --source <file or folder> [--due YYYY-MM-DD] [--agency …]` creates a calls row with portal 'manual' and id 'manual-<slug>', copies the source files into `work_dir/source/`, and queues a draft. `build_inputs` reads a manual call's listing and attachments from source/ instead of a portal. This is how the team drafts against a solicitation no scanner found, such as an emailed RFP.
5. Open a PR to the Coordinator that adds the worker to `scripts/install-schedule.ps1` as an always-on task named `velocity-bd-team-draft-worker` (start at logon, restart every minute on failure, no execution time limit).
6. Tests (fake model client, SQLite): two workers claiming at once start only one draft; a second request for the same call is refused while one is active; cancelling a queued draft needs no worker; a stale running draft is reaped; a retry after a failure in Review ×4 resumes there; the cost gate holds a draft in needs_approval and approve releases it; an approved draft request becomes a queued draft and the request shows applied, while one for a call marked not relevant fails with the reason.

## Done when

- With the worker running, `request --call-id <a real pursued Vulcan call>` takes the draft from queued to completed. `status` during the run shows the phase and elapsed time; you show the final row with its phase_log, cost_usd and result.
