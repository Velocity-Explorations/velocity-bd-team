Vulcan SOF Agent Playbook

Ten self-contained prompts that take an agent from an empty repository to a scheduled scanner that logs into Vulcan SOF, scrapes open calls, judges fit, delivers results to Slack, learns from the team's reactions, and shows everything in a dashboard. One repo, one database as the contract between every part. Each prompt restates its own context, so it can be pasted into a fresh session.

How to use this

  • Run the phases in order. Each one builds on files and database tables the previous phase produced, and each prompt says what it expects to already exist.
  • Paste one prompt per session or turn. Every prompt carries its own context block, so nothing depends on the agent remembering earlier chats.
  • Each prompt ends with explicit "Done when" criteria. Don't move on until the agent has shown the evidence those criteria ask for.
  • The ledger (Phase 0) is the spine. Every later phase reads and writes it; nothing passes between stages as loose JSON files.
  • The prompts say "whatever mail / model / alert access this environment has" so they work for any agent. Put the concrete answers in AGENTS.md once (block below) and every phase inherits them.
  • Anything you have to do yourself is in an orange Your part box. The setup section right below collects the ones that happen before a phase starts; the boxes inside each phase cover what you do during and after it.

The team of agents

One agent per portal, a coordinator over them, and a few specialists that own the parts of the pipeline every portal shares. Each agent owns a directory; everyone else changes that directory only through a pull request. The ledger is the only thing they all touch, and only the coordinator changes its schema.

AgentOwnsJobBuilds
Coordinatorrun.py, ledger/, AGENTS.md, docs/, the schedulerRuns the pipeline, watches the runs table, alerts on failures, merges PRs, is the only one who changes the schema, keeps docs/STATUS.md currentPhases 0, 7
Portal agents (one each: Vulcan SOF first, then SAM.gov, NSTXL, DIU, AFWERX…)portals/<slug>/Log in, scrape, filter for that portal; produce calls rows in the shared record shape; fix the scraper when the site changesPhases 1 to 5 per portal

Librarianlibrary/Drive sync, register sync, extraction, embeddings, exemplar retrieval; keeps the past-proposal memory accurateProposal Library plan A to F

Dashboarddashboard/, slack/Everything the humans see: Slack cards, the web app, the triage actionPhases 8 (delivery half), 9

Two cautions

  1. Don't start with six agents. Every agent adds coordination cost. Start with the Coordinator and the Vulcan portal agent (that's this playbook, Phases 0 to 7), add the Reviewer at Phase 6 if you want it separated, and bring in the Librarian, Dashboard, and Writer as their plans begin. Add the second portal agent only after Vulcan runs unattended for a few weeks.
  2. Specialize by what changes independently, not by what sounds tidy. Portals change on their own schedule, so one agent each is right. The review prompt, the Proposal Library, and the dashboard each change for their own reasons too. Splitting further (a "QA agent", a "schema agent") adds overhead without a boundary that earns it; those are the Coordinator's job.

Who's missing on purpose

  1. A Capture agent (go/no-go recommendation with pricing, teaming, and bid-strategy) is a plausible seventh role once the Writer exists and the Proposal Library has outcomes to learn from. Not before.
  2. A Compliance agent (checks a draft against every "shall" in the solicitation) is already a phase inside the Writer's pipeline; it only becomes its own agent if the Writer gets too large.

PHASE 00

Repo and ledger foundation

Everything else writes into the database this phase creates, and the dashboard reads from it, so the schema is the one contract in the system. It's designed wider than "scraped calls" on purpose: it already has a proposals table for the Proposal Library plan, so that work slots in without a migration later.

Postgres is specified because the dashboard needs to reach the database from wherever it's hosted. A free Neon or Supabase instance is enough. SQLite remains available for local development only.

Depends on: nothing. Produces: the repository, DATABASE_URL, the schema, a migration runner, query helpers, and docs/LEDGER_SCHEMA.md.
Prompt · Phase 00
You are building `velocity-bd-team`, a single repository that will hold a government-opportunity scanner, an LLM reviewer, a Slack delivery/feedback loop, a Proposal Library of past proposals, and a dashboard. This is Phase 0 of 9: create the repository and the shared database ("the ledger") that every later phase reads and writes. No scraping happens in this phase.

## Context

Velocity Explorations is a small defense software company. The scanner will log into portals such as Vulcan SOF (USSOCOM's industry engagement site), scrape open "calls," filter and review them for fit, and surface them to the team. The team's decisions flow back into the database. A dashboard later reads the same database directly; there is no API layer between components. The database is therefore the one contract in the system, and its schema must be documented well enough that someone could build a dashboard from the document alone.

Database: PostgreSQL, reached via a `DATABASE_URL` in `.env` (a hosted free-tier instance such as Neon or Supabase is expected). Code must also run against SQLite (`DATABASE_URL=sqlite:///data/dev.db`) for local tests, so write portable SQL: TEXT/INTEGER/REAL/TIMESTAMP columns, no Postgres-only types except where noted, JSON stored as TEXT.

## Tasks

1. Initialize the repo with this layout (create empty packages where noted):

2. `ledger/schema.sql`: three tables, every timestamp ISO-8601 UTC text:

   runs(
     id INTEGER PRIMARY KEY (autoincrement/serial), component TEXT (e.g. 'vulcan_sof','review','library','pipeline'),
     portal TEXT, started_at, finished_at,
     status TEXT CHECK IN ('running','completed','skipped_timeout','error'),
     stage_counts TEXT (JSON: {"fetched":N,"filtered":N,"reviewed":N,"new":N}),
     error TEXT, log_path TEXT, dry_run INTEGER DEFAULT 0 )

   calls(
     id TEXT PRIMARY KEY,                 -- e.g. "vulcan-<collectionUuid>"; stable across runs
     portal TEXT, title TEXT, type TEXT, department TEXT, naics_code TEXT, set_aside TEXT,
     posted_date TEXT, due_date TEXT, description TEXT, url TEXT, source_type TEXT,
     first_seen_at, last_seen_at, first_run_id INTEGER, last_run_id INTEGER,
     filter_result TEXT CHECK IN ('pending','kept','rejected') DEFAULT 'pending',
     filter_reason TEXT, match_tier TEXT, matched_keywords TEXT (JSON array),
     ai_verdict TEXT CHECK IN ('yes','no','maybe') NULL, ai_reasoning TEXT, reviewed_at,
     slack_channel TEXT, slack_ts TEXT, posted_at,
     human_status TEXT CHECK IN ('pursue','not_relevant','submitted','dismissed') NULL,
     human_by TEXT, human_at, human_notes TEXT,
     extra TEXT (JSON; portal-specific fields with a key prefix such as "vulcan_"; never add portal-specific columns),
     updated_at )

   proposals(                             -- past submissions; filled by the Proposal Library plan
     submission_id TEXT PRIMARY KEY,      -- "YYYY-MM-DD_portal_short-title", matches a Drive folder name
     title, portal, agency, solicitation_id, type, role, partners, submitted_date, due_date,
     requested_value TEXT, outcome TEXT CHECK IN ('won','lost','no_award','pending','withdrawn','shortlisted') NULL,
     outcome_date, award_value TEXT, strength_rating INTEGER (1 to 5), strength_reason TEXT,
     why_won_or_lost TEXT, use_as_exemplar INTEGER DEFAULT 0, themes TEXT, drive_link TEXT,
     brief TEXT,                          -- one-paragraph summary generated later
     synced_at, updated_at )

   Add indexes on calls(portal, first_seen_at), calls(human_status), calls(ai_verdict), proposals(portal, outcome).
3. `ledger/migrations/001_initial.sql` holds the schema above; `ledger/migrate.py` applies every `NNN_*.sql` in order that isn't yet recorded in a `schema_migrations` table. Running it twice is a no-op. Works against both Postgres and SQLite. Later schema changes are new numbered files, additive only (see AGENTS.md).
4. `ledger/db.py`: `connect()` returning a DB-API connection from DATABASE_URL (psycopg for postgres://, sqlite3 for sqlite://), a `tx()` context manager that commits/rolls back, and a tiny `q(sql, params)` helper that normalizes the `?` vs `%s` placeholder difference so queries.py is written once.
5. `ledger/queries.py`: the functions later phases will call. Implement and unit-test each:
   runs:  `start_run(portal, dry_run) -> id`, `finish_run(id, status, stage_counts, error=None, log_path=None)`
   calls: `upsert_call(record, run_id) -> bool is_new` (insert if absent and set first_seen/first_run; otherwise update scraped fields and last_seen/last_run, NEVER touching filter_*, ai_*, slack_*, human_* columns),
          `set_filter(id, result, reason=None, tier=None, keywords=None)`, `set_review(id, verdict, reasoning)`,
          `set_slack(id, channel, ts)`, `set_human(id, status, by, at)`, `append_note(id, text, by, at)` (appends with timestamp),
          `calls_for_review(run_id)` (kept, unreviewed), `new_calls(run_id)` (first_run_id = run_id and verdict in yes/maybe),
          `pending_feedback()` (slack_ts set, human_status null), `recent_decisions(limit=20)`,
          `export_csv(path)`.
   proposals: `upsert_proposal(row)`, `list_proposals(portal=None, outcome=None)`.
6. `docs/LEDGER_SCHEMA.md`: every table, every column, allowed values, which component writes it, and a short "how to build a dashboard against this" section with three example queries (new calls this week, triage backlog, win rate by portal).
7. `README.md`: purpose, layout, setup (.env, migrate), and the rule that components communicate only through the ledger.

## Context

Vulcan SOF (https://vulcan-sof.com) is USSOCOM's industry engagement portal where SOF organizations post "calls" (problem statements, RFIs, prototype opportunities). It is an Angular single-page app served under /login/ng2/. Key URLs:

- Login page:     https://vulcan-sof.com/login/ng2/auth/login
- Calls listing:  https://vulcan-sof.com/login/ng2/search/calls
- Call detail:    links whose href contains collectionUuid=<uuid>

Authentication is username + password followed by a 6-digit one-time code emailed to the account owner (Phase 2). The reference implementation used Python 3.11 with Playwright and headless Chromium; use the same unless the runtime forbids it.

Two rules that apply to every phase, learned from a scan that hung for three days:
1. NEVER wait for Playwright's "networkidle" state on this site. The Angular app keeps background XHR/WebSocket traffic alive, so networkidle never fires. Use wait_for_load_state("domcontentloaded") followed by a fixed wait_for_timeout() of 1.5 to 3 seconds.
2. Every navigation and every wait gets an explicit timeout. Nothing may block indefinitely.

## Context

Vulcan SOF (https://vulcan-sof.com) is an Angular SPA under /login/ng2/.
- Login page:    https://vulcan-sof.com/login/ng2/auth/login
- Calls listing: https://vulcan-sof.com/login/ng2/search/calls  (only reachable when logged in)

Auth flow: enter username and password, press Enter. The account requires 2FA, so the page then shows a one-time-code screen. Form discovery:

- The password field may not be visible until the username is filled. After filling the username, if the password input is not visible, wait up to 10s for `input[type='password']:visible`.
- Fill password, press Enter, wait 3s.

OTP detection:
- Record `login_triggered_at = time.time()` immediately before filling the username.
- After submitting, read `document.body.innerText`. If it contains "passcode", "one-time", or "verification" (case-insensitive), the OTP screen is showing.

OTP entry (Angular quirks):
- Code input cascade: `input[name*='otp']`, `input[name*='code']`, `input[name*='passcode']`, `input[type='tel']`, `input[type='number']`, `input[type='text']`, any `input`.
