Why this upgrade

Since 17 Oct the dashboard is the only place decisions are made. Slack posts cards, run summaries and progress, but its reactions are not read. The Writer Plan still needs one thing the system doesn't have:

  • A draft queue. A draft takes 20 to 60 minutes and costs real money, so it needs somewhere to queue, show progress, cancel, retry and wait for approval. Requests arrive three ways: the dashboard's Draft button, the command line, and draft requests from the portal assistant that a person approves on the dashboard's Requests page. Those already exist as change_requests rows of kind draft, built on 17 Oct.

## Context

- Decisions are made on the dashboard, and Slack reactions are not read. A draft request arrives from the dashboard's Draft button, from the command line, or as an approved `change_requests` row of kind 'draft', which the Writer's worker turns into a queued draft (Writer Plan W2a).
- The Writer Plan needs a `drafts` queue: one row per draft request, with progress, cancel, retry and approval.
- Writer Phase W3 links a proposal to its call through `proposals.source_call_id`, which doesn't exist yet.

## Tasks

1. New migration `ledger/migrations/<next number>_drafts.sql`, additive only and portable between Postgres and SQLite (timestamps ISO-8601 UTC text, JSON stored as TEXT, `@@AUTOINCREMENT@@` on the key):

   drafts(                                -- draft requests and their progress; the Writer's queue
     id INTEGER PRIMARY KEY @@AUTOINCREMENT@@, call_id TEXT,
     requested_by TEXT, requested_via TEXT CHECK IN ('dashboard','assistant','cli'), requested_at,
     request_id INTEGER NULL,             -- the change_requests row an assistant request came from
     status TEXT CHECK IN ('queued','needs_approval','running','completed','failed','cancelled') DEFAULT 'queued',
     resume_of INTEGER NULL,              -- the failed or cancelled draft this one continues
     work_dir TEXT, estimate_usd REAL, approved_by TEXT, approved_at,
     started_at, finished_at, heartbeat_at, worker_pid INTEGER,
     current_phase TEXT,
     phase_log TEXT (JSON array, one entry per phase: id, name, status, started_at, finished_at, seconds, chars_in, chars_out),
     cancel_requested_by TEXT, cancel_requested_at,
     status_channel TEXT, status_ts TEXT, -- the Slack message that shows this draft's progress
     result TEXT (JSON: word_count, page_estimate, page_limit, compliance_open_items, alignment_fit),
     drive_folder_url TEXT, submission_id TEXT, cost_usd REAL, error TEXT,
     updated_at )

   Add proposals.source_call_id (ALTER TABLE proposals ADD COLUMN source_call_id TEXT).
   Indexes: proposals(source_call_id), drafts(status), drafts(call_id), and one active draft per call:
   CREATE UNIQUE INDEX drafts_one_active ON drafts(call_id) WHERE status IN ('queued','needs_approval','running');
2. `ledger/queries.py`, each helper returning (draft_id, None) or (None, reason):
   - `request_draft(call_id, by, via, request_id=None, force=False)`: refuses calls whose human_status is not_relevant, dismissed or submitted (force skips this, for the CLI) and calls that already have a queued, needs_approval or running draft; otherwise sets human_status to 'pursue' if it is empty and inserts a queued draft.
   - `request_cancel(call_id, by)`: a queued or needs_approval draft becomes 'cancelled' at once; a running one gets cancel_requested_by and cancel_requested_at, and the worker stops it.
   - `request_retry(call_id, by, via)`: a new queued draft with resume_of set to the call's latest failed or cancelled draft; refused if there is none or a draft is active.
   - `approve_draft(draft_id, by)`: needs_approval back to queued, with approved_by and approved_at; callers decide who may approve.
3. `docs/LEDGER_SCHEMA.md`: document the table, the one-active-draft rule and source_call_id, and add a "Requesting a draft from SQL" section with the exact statements the dashboard uses to request, cancel, retry and approve, following the same rules as the Python helpers.
4. Tests (pytest, SQLite): request_draft refuses a second active draft for a call and refuses a call marked not_relevant; it marks an undecided call pursue; request_cancel on a queued draft cancels it at once; request_retry points resume_of at the failed draft; approve_draft releases a needs_approval draft; upsert_proposal without source_call_id leaves it unchanged.

## Done when

- `python -m ledger.migrate` applies the new migration on Postgres and on SQLite, a second run reports nothing to do, and `python -m ledger.migrate --list` shows drafts.
- The new tests and every existing test pass.
- Scans, the dashboard and `run.py --apply-requests` behave exactly as before.
- The PR description lists anything in the existing ledger that differed from this prompt.
